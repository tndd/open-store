# 認証システム設計

## 概要

Open Storeの認証システムは、開発効率と実用性を両立するため、開発環境と本番環境で異なるアプローチを採用する。

## 段階的認証実装戦略

このプロジェクトでは、開発環境と本番環境で異なる認証方式を採用することで、開発効率とリスク管理を両立する。

### 開発環境（dev）: 簡易認証モック

- **目的**: BUY権限機能の動作確認とUI/UX検証
- **実装**: 登録済みユーザーからの選択式ログイン
- **技術**: localStorage等による簡易セッション管理
- **利点**: 
  - 認証の複雑さを排除してコア機能開発に集中
  - UI/UXの検証が可能
  - 動作するプロトタイプの早期完成

### 本番環境（prod）: 本格認証実装

- **目的**: 本番環境での実用化
- **実装**: Auth.js + マジックリンク認証
- **移行**: 開発環境で確立したUI/UX基盤を活用

## 本番環境の技術仕様

### 認証システム

認証システムには、**Auth.js（NextAuth）+ マジックリンク認証**を使用する。

**技術仕様:**
- **認証プロバイダー**: Auth.js EmailProvider
- **セッション管理**: JWT（JSON Web Token）
- **メール送信**: SendGrid / Resend / Amazon SES等
- **セッション有効期限**: 90日間
- **マジックリンク有効期限**: 15分間

### セキュリティ対策

- **HTTPS必須**: 本番環境では必ずHTTPS通信
- **CORS設定**: 許可されたドメインからのみAPI呼び出し可能
- **CSP設定**: Content Security Policyでスクリプト実行を制限
- **Rate Limiting**: メール送信の頻度制限
- **メール検証**: 一意制約により重複登録を防止

## 設計思想

### アカウント作成の障壁軽減

- アカウント作成は煩わしいものでパスワード管理も大変
- そこでユーザーはメールアドレスのみでログインまでを行うことができるようにする

### ユーザーのデフォルト設定

- デフォルトのユーザー名はメールアドレスの@の前部分として設定される
- 配送先は**初注文の時に**入力をしてもらう形にする
- 登録を段階的に行わせることで、さらに登録障壁を下げる

## 画面設計

### ログイン画面

#### 開発環境（dev）: 簡易認証モック版
- 登録済みユーザー一覧（ドロップダウンまたはカード選択）
- 「ログイン」ボタン
- 「認証機能は簡略化されています」注意表示

#### 本番環境（prod）: 本格認証版
- メールアドレス入力フィールド
- マジックリンク送信ボタン
- 「マジックリンクを送信しました」メッセージ表示

## データベース連携

### User-Address段階的登録

- **新規ユーザー作成時**: メールのみでUser作成、address_id=NULL
- **初回購入時**: 住所入力 → Address作成 → User.address_id更新の順次処理
- **⚠️重要**: Address初登録時のaddress_id登録漏れに注意すること

詳細なテーブル設計については`database.md`を参照してください。
